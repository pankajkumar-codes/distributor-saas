# ADR 0001: Commerce data model

- Status: **Proposed** (needs owner approval; see "Approval needed" at the end)
- Date: 2026-10-14
- Author: Staff Engineer (contract owner). Implementation: Lead Engineer, per
  `team/engineering.md` ownership; Staff reviews commerce schema PRs against this ADR.
- Related: D-004, D-009 to D-015 in `docs/DECISIONS.md`; `docs/DOMAIN_MODEL.md`;
  `docs/BUSINESS_RULES.md` sections 1 to 10; `docs/ARCHITECTURE.md`

## Context

`docs/ARCHITECTURE.md` puts everything that changes stock or money in one service,
**commerce**, so that finalizing an invoice, moving its stock and allocating its
payment commit in one PostgreSQL transaction. This ADR turns the conceptual model in
`docs/DOMAIN_MODEL.md` into a concrete relational design for that service: tables,
keys, lifecycle rules, how each business invariant is enforced, and which parts are
still waiting on blocking decisions.

Several decisions that shape the schema are still open (invoice-numbering scope
D-010, reservation and deduction events D-011, negative stock D-012, costing D-013,
batches D-014). The design below does not answer them. It makes each one a
**per-tenant configuration value or a nullable column** that the schema already
supports, so the answer changes data, not tables. Where that is not possible, it says
so.

A runnable sketch of the core tables is in
`services/commerce/design/0001_commerce_schema_sketch.sql`. It is not a migration
(the migrator only reads `migrations/`), and `services/commerce/tests/test_schema_sketch.py`
checks the invariants below against a real PostgreSQL in CI.

## Decision

### 1. Conventions that apply to every table

| Concern | Rule |
|---|---|
| Keys | `id uuid` primary key, generated by the service (UUIDv7 once available in the stdlib; v4 until then). No sequences leak row counts across tenants. |
| Tenancy | Every table has `tenant_id uuid not null`. Every table also has `unique (tenant_id, id)`, and **every foreign key is composite** `(tenant_id, x_id) references t (tenant_id, id)`. The database then rejects a reference to another tenant's row even if the service forgets to check (CLAUDE.md rule 8). |
| Row-level security | Policy on every table: `tenant_id = current_setting('app.tenant_id')::uuid and identity.is_member(tenant_id)`. The service sets `app.user_sub` and `app.tenant_id` per transaction. `identity.is_member` is a `security definer` function, so the identity migration only needs `grant execute ... to svc_commerce`; commerce gets no grants on identity tables. |
| Money | `numeric(18,2)` in INR for amounts, `numeric(18,4)` for unit prices, `numeric(7,4)` for rates (18% is `18.0000`). Python side uses `platform_common.money`; floats are rejected. One currency (`INR`) for now, stored explicitly as `currency char(3) check (currency = 'INR')` so foreign currency is an additive change. |
| Quantity | `numeric(18,3)` in the product's base unit of measure. Never float. |
| Rounding | Not decided (BUSINESS_RULES section 6). Each document stores the `rounding_mode` and `rounding_level` (line or document) it was calculated with, so a finalized document can be recomputed exactly even after the tenant default changes. |
| Time | `timestamptz` for events, `date` for business dates (invoice date, receipt date). Every document keeps both, because "when it happened" and "when we recorded it" differ for late imports. |
| Who | `created_by`, and for documents `finalized_by` / `cancelled_by`, hold the Cognito `sub`. |
| Deletes | `svc_commerce` gets **no `delete` grant** on documents, lines, movements, payments, allocations or audit. Drafts are discarded by status, not deleted. |

### 2. Tables by area

**Configuration** (rarely written; owner/admin only)

- `legal_entities`: legal name, PAN, address. MVP UI creates exactly one per tenant;
  the schema allows more (open question 16).
- `gst_registrations`: GSTIN, state code, legal entity, valid from/to. Nullable for
  unregistered businesses.
- `locations`: warehouse/store, belongs to a legal entity.
- `financial_years`: code (for example `2026-27`), start and end date, per legal entity.
- `number_series`: see section 4.
- `tenant_settings`: one row per tenant holding the policy switches the blocking
  decisions will fill in: `negative_stock_policy` (`forbid` | `warn` | `role`),
  `default_rounding_mode`, `default_rounding_level`, `costing_method`. Defaults are the
  safest choice (`forbid`, no costing method set) until the owner decides.

**Catalog and parties**

- `products`: internal SKU (unique per tenant), name, unit, HSN code, tax
  classification reference, `tracks_batches boolean` (D-014), status.
- `channels`: Amazon, Flipkart, Meesho, direct wholesale; per tenant.
- `channel_sku_mappings`: `(tenant, channel, external_sku)` unique, points to a
  product. Unmapped SKUs block an import row rather than guessing (rule 10).
- `parties`: one table for customers and suppliers with `is_customer` /
  `is_supplier` flags and GSTIN, because distributors routinely buy from and sell to
  the same business and the alternative is duplicate records that drift. Contact and
  address details live here; documents snapshot what they used.

**Documents** (two families, because numbering and issuer differ)

- `sales_documents` + `sales_lines`: types `invoice`, `credit_note`, `debit_note`.
  Numbered by us from a `number_series` on finalization.
- `purchase_documents` + `purchase_lines`: types `supplier_invoice`,
  `supplier_credit_note`, `purchase_return`. Carry the **supplier's** number, unique per
  `(tenant, supplier, supplier_doc_number, financial_year)`, so the same bill cannot
  be entered twice.
- Lines store a snapshot of everything used in the calculation: product SKU and name,
  HSN, unit, quantity, unit price, discount, taxable value, tax rate(s) and tax amounts,
  and the tax rule id and version that produced them. Changing a product later never
  rewrites a finalized document.
- Tax columns are generic (`tax_component` rows on each line: component code, rate,
  amount) instead of fixed `cgst`/`sgst`/`igst` columns. Which components apply is a
  tax-rule decision (D-005, rule 12), not a schema decision.
- Credit and debit notes reference the original document (`original_document_id`).

**Stock**: section 5. **Payments**: section 6.

**Marketplace** (kept separate on purpose, CLAUDE.md rule 11)

- `external_orders` + `external_order_lines`: source platform status and timestamps,
  unique `(tenant, channel, external_order_id)`.
- `external_invoice_refs`: invoice number, issuer (seller, marketplace, unknown), date.
  Recorded, never generated by us, until D-009 says otherwise.
- `marketplace_settlements` + `settlement_lines`: one line per component (sale, tax,
  fee, refund, reserve, adjustment), each with the external reference it reconciles to.
- `bank_payouts`: amount, UTR/bank reference, linked to the settlement it pays.
- These five never share a row. A report joins them; it never collapses them.

**Plumbing**

- `idempotency_keys`, `inbox_messages`, `outbox_events`: section 7.
- `audit_events`: same shape as `identity.audit_events`, append-only, written in the
  same transaction as the change it describes.

### 3. Document lifecycle

```
draft ──finalize──▶ finalized ──cancel──▶ cancelled
  │
  └──discard──▶ discarded
```

- **Draft**: freely editable, no number, no stock or money effect.
- **Finalize** is one transaction: lock the draft, re-validate, compute totals with the
  stored rounding policy, allocate the number (section 4), write stock movements
  (section 5), write the outbox event, write the audit event. Any failure rolls all of
  it back, so there is never a numbered invoice without its stock effect or the
  reverse (BUSINESS_RULES section 5).
- **Finalized** rows are immutable. A trigger rejects any `update` on a finalized
  document or its lines, except the single transition to `cancelled` which may only
  set `status`, `cancelled_at`, `cancelled_by` and `cancel_reason`. This is enforced in
  the database, not only in code.
- **Cancel** writes compensating stock movements and releases payment allocations by
  appending reversal rows. Whether a given correction must be a cancellation or a
  credit note is a legal question (D-010); the schema supports both.

### 4. Invoice numbering

- `number_series` has: `doc_type`, `financial_year_id`, nullable `legal_entity_id`,
  nullable `gst_registration_id`, nullable `location_id`, `prefix`, `next_value`,
  `padding`, `status`.
- **Which of those columns define the scope is D-010.** Whatever the answer, it becomes
  a partial unique index on the series columns plus a validation rule that picks the
  series for a document. No table changes.
- Allocation: `update number_series set next_value = next_value + 1 where id = $1
  returning next_value - 1` inside the finalize transaction. The row lock serializes
  concurrent finalizations on the same series, and a rollback returns the number, so
  numbers are gapless and never reused for a committed document.
- `sales_documents` has `unique (tenant_id, series_id, sequence_no)` and a stored
  `document_number` (prefix + padded sequence) that is also unique per series.
- Contention: one series is one row lock, so finalizations within a series run one at a
  time. At 1 to 20 users per tenant that is milliseconds of waiting; revisit only if
  bulk finalization becomes a feature.

### 5. Stock ledger

- `stock_movements` is the source of truth and is append-only (no update, no delete
  grant; trigger rejects updates).
- Columns: product, location, `stock_state` (`sellable` | `quarantine` | `damaged`),
  `on_hand_delta`, `reserved_delta`, `movement_type`, `occurred_at`, `recorded_at`,
  optional `batch_id`, `unit_cost` (inbound only), and the source:
  `source_type`, `source_id`, `source_line_id`.
- Two deltas on one row means "ship 5 that were reserved" is a single atomic row
  (`on_hand -5, reserved -5`) instead of two rows that could be half-written.
  `available = on_hand - reserved`, shown separately as PRD section 6 requires.
- Movement types: `opening`, `purchase_receipt`, `purchase_return`, `sale_reserve`,
  `sale_release`, `sale_issue`, `sale_return_receive`, `restock` (quarantine to
  sellable), `write_off`, `adjustment`, `transfer_out`, `transfer_in`, `reversal`.
  Which business event triggers `sale_reserve` vs `sale_issue` per channel is D-011;
  the ledger supports any mapping.
- Returns land in `quarantine`; only an explicit `restock` makes them sellable
  (BUSINESS_RULES section 4).
- **Idempotency**: `unique (tenant_id, source_type, source_id, source_line_id,
  movement_type)`. A retried receipt or import hits the constraint and the service
  treats it as "already done". This is the "purchase receipt changes stock once"
  success criterion, enforced by the database.
- **Corrections**: a `reversal` row with `reverses_movement_id` (unique, so a movement
  can be reversed only once) and the negated deltas.
- `stock_balances (tenant, product, location, stock_state)` holds running totals,
  updated in the same transaction as each movement. It exists for one reason: it is
  the row the service locks (`select ... for update`) to stop two concurrent orders
  overselling, and where the negative-stock policy (D-012) is checked. It is never the
  only record; a reconciliation query must always equal the ledger sum, and a test
  enforces it.
- **Cost**: inbound movements carry `unit_cost`. COGS and valuation are computed by
  the costing method (D-013, proposed weighted average) from the ledger; no cost is
  written on outbound movements until that decision is approved, so nothing has to be
  rewritten if the method changes.
- **Batches** (D-014): optional `batches` table (product, batch code, expiry) and a
  nullable `batch_id` on movements and balances. Off unless a product sets
  `tracks_batches`.

### 6. Payments

- `payments`: direction (`received` | `paid`), party, method, date, amount (> 0),
  external reference (UTR, cheque no.), status.
- `payment_allocations`: payment, document (sales or purchase), amount. Append-only;
  an un-allocation is a new row with a negative amount referencing the one it
  reverses.
- **Over-allocation** is prevented by locking the payment row and the document row
  (in that order) and checking `sum(allocations) + new <= payment.amount` and
  `<= document outstanding` in the same transaction. A plain check constraint cannot
  express a sum across rows, so this one is enforced by the service under lock, with a
  test that runs two allocations concurrently.
- The unallocated part of a payment is an advance. It is reported, never silently
  applied.
- Refunds are payments in the opposite direction linked to a credit note, not edits of
  the original payment.

### 7. Idempotency between imports and commerce, and events out

Requests arrive from three places: the API (people), the imports service (confirmed
rows), and retries of either. Three mechanisms, each for one job:

1. **Natural keys** (strongest, always on): external order id per channel, supplier
   document number per supplier and year, movement source key. These make duplicates
   impossible regardless of how the request arrived.
2. **`idempotency_keys`** `(tenant_id, key)` primary key, plus `request_hash` and
   `response`. Every mutating API call and every import hand-off carries a key (for
   imports: `import_run_id:row_number`). Same key and same hash returns the stored
   response; same key with a different hash is a `409`, because it means the caller
   changed the payload under the same key, which must not be guessed about
   (CLAUDE.md rule 10).
3. **`inbox_messages`** `(tenant_id, message_id)` primary key for SQS deliveries, which
   are at-least-once. The insert happens in the same transaction as the effect.

Events out (for example `sales_document.finalized` to the documents service) are
written to `outbox_events` in the finalize transaction and published to SQS by a
relay afterwards. Publishing directly from the request would either lose the event
when SQS fails after commit or announce an invoice that then rolled back. Consumers
must be idempotent on `event_id`.

Imports keep their own staging tables in their own schema and own the
preview/validation flow. Commerce never reads the imports schema; every import row
references `import_run_id` and `source_row` in the commerce record it created, so a
stock movement or order traces back to the file and row it came from.

### 8. Locking order

To avoid deadlocks, every transaction that touches more than one of these takes locks
in this order: `number_series`, then the document, then `stock_balances` rows sorted
by `(product_id, location_id, stock_state)`, then `payments`.

## Options considered

| Choice | Picked | Rejected and why |
|---|---|---|
| Customer and supplier | One `parties` table with role flags | Two tables: simpler per query, but the same business buying and selling ends up as two records that drift. |
| Document tables | Sales and purchase families | One `documents` table: numbering, issuer and validation differ enough that most columns would be nullable for one side. A table per document type: too much duplication of lines and tax logic. |
| Tax amounts | Component rows | Fixed `cgst`/`sgst`/`igst`/`cess` columns: bakes a tax interpretation into the schema (rule 12). |
| Reservations | Second delta on the movement row | Separate reservations table: shipping a reserved unit would need two writes in two tables that must stay in sync. |
| Balances | Ledger plus locked balance row | Ledger only with `sum()` on every check: correct but needs table-level locking or serializable isolation to prevent overselling; slower as history grows. |
| Cross-tenant safety | Composite foreign keys plus RLS | RLS alone: protects reads but a bug could still link tenant A's document to tenant B's product id. |
| Accounting ledger | None now (D-015) | Double-entry journal: out of scope until an accounting product is chosen; exports read documents, payments and settlements directly. |

## Consequences

- Positive: every invariant in BUSINESS_RULES sections 1, 4, 5 and 10 has a database
  constraint, trigger or lock behind it, not only application code.
- Positive: the blocking decisions become configuration rows, so answering them does
  not need a destructive migration.
- Negative: composite foreign keys make every join carry `tenant_id`. That is intended,
  but it is more verbose, and ORM models must declare the composite keys.
- Negative: SQLite cannot run these tests (no RLS, triggers differ). Commerce tests that
  touch the database need PostgreSQL; CI already has it.
- Negative: the service, not the database, enforces payment over-allocation. It needs a
  concurrency test before payments ship.

## Approval needed

Per the CLAUDE.md approval gates, these need the owner's yes before the first commerce
migration is written:

1. This overall model (tables, lifecycle, immutability rules).
2. Accounting posting semantics: no general ledger; documents, payments and
   settlements are the records exports read (D-015).
3. Default policies until the blocking decisions are answered: negative stock
   **forbidden**, no costing method applied, invoice finalization **disabled** until
   D-010 picks the numbering scope.

These stay blocked and are not answered by this ADR: D-009 (invoice issuer per
marketplace), D-010 (numbering scope), D-011 (reservation and deduction events),
D-012 (negative stock policy), D-013 (costing), D-014 (batches), and the GST scenarios
in scope (open question 8).
